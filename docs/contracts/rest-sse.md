# REST and SSE contract

Freezes section 8 of the MVP. It covers the 20 endpoints, the envelopes, the states and the
error catalogue. The examples cited here live in `examples/` and are validated with
`spike/fase0/tools/validate_contracts.py`.

## 1. Conventions

- Base: `/api`. Bodies and responses in `application/json; charset=utf-8`.
- Dates: ISO-8601 in UTC, `Z` suffix (`emittedAt`, `generatedAt`, `computedAt`).
- Units: the ones in `world-graph-rules.md`. Money is always whole euro cents; the
  solver objective uses its own integer units, never euros.
- Every mutation returns the complete **atomic snapshot** of the new
  `ScenarioRevision`. The frontend never rebuilds partial state.
- Every command carries `commandId` and `scenarioRevision`. That is the mechanism that
  lets stale results be discarded.
- Forbidden: the browser does not choose the model and does not send `model`, `think`,
  `options` or `keep_alive`.

## 2. Command envelope

Every state-mutating `POST`/`PATCH`/`DELETE` uses this envelope (schema:
`schemas/envelopes.schema.json#/$defs/commandEnvelope`):

```json
{
  "commandId": "3f1c0b6a-4f4d-4d4f-9a2f-2f6a6c9d9b21",
  "scenarioRevision": 4
}
```

| Field | Type | Rule |
|---|---|---|
| `commandId` | UUID v4 | required; generated by the client; identifies the logical attempt |
| `scenarioRevision` | integer ≥ 0 | required; last revision the client has applied |

Semantics:

1. The server applies the command to the current state and replies with the resulting
   revision. It does not reject a command for being "one revision behind": the user
   gesture is the intent and the returned snapshot is authoritative.
2. The `appliedAgainstRevision` field of the response states which revision it was
   really applied against. If it differs from the `scenarioRevision` that was sent,
   `rebased` is `true` and the frontend must accept the new snapshot and discard any
   earlier in-flight response.
3. **Idempotent retry:** repeating the same `commandId` does not mutate the state
   again. The server returns the stored result with `replayed: true`. The idempotency
   window is the lifetime of the scenario.
4. `DELETE /api/scenarios/{scenarioId}` does not require an envelope: it is a reset
   operation on the resource. Everything else does.

## 3. Response envelope

Schema: `schemas/envelopes.schema.json#/$defs/successResponse`. Example:
`examples/mutation-response-barrier.example.json`.

```json
{
  "scenarioId": "0f1a...-...",
  "scenarioRevision": 5,
  "previousRevision": 4,
  "emittedAt": "2026-09-22T09:10:44.512Z",
  "appliedCommand": {
    "commandId": "3f1c0b6a-4f4d-4d4f-9a2f-2f6a6c9d9b21",
    "kind": "BARRIER_PLACED",
    "appliedAgainstRevision": 4,
    "rebased": false,
    "replayed": false
  },
  "revision": { "...": "complete ScenarioRevision" },
  "result": { "...": "endpoint-specific object or absent" }
}
```

`GET /api/scenarios/{scenarioId}` does not wrap: it returns a
`ScenarioRevision` (`schemas/scenario-revision.schema.json`).

## 4. Rules for discarding stale results

Mandatory in the frontend, and verifiable in Phase 6/9 with tests:

1. Keep `maxAppliedRevision` per scenario. Discard any payload whose
   `scenarioRevision` is lower. At equal revision, the last one received wins.
2. Keep `maxAppliedTick` inside the current revision. Discard simulation events with
   `tick <= maxAppliedTick`.
3. A direct command response is only applied if its `commandId` matches the pending
   command; an old `commandId` is discarded without touching the UI.
4. After a `scenario.resync` event, the client calls `GET /api/scenarios/{id}` and
   sets `maxAppliedRevision` from what it received before repainting.
5. A discard is never presented to the user as an error: it is the expected behaviour
   of a lost race.

## 5. Error catalogue

Schema: `schemas/envelopes.schema.json#/$defs/errorResponse`; example:
`examples/error-response.example.json`.

```json
{
  "error": {
    "code": "SNAP_OUT_OF_RADIUS",
    "message": "The drop point is 31.4 m away from the nearest valid node.",
    "details": { "distanceMeters": 31.4, "maxRadiusMeters": 12.0 },
    "scenarioRevision": 4,
    "commandId": "3f1c0b6a-4f4d-4d4f-9a2f-2f6a6c9d9b21",
    "retryable": false
  }
}
```

| Code | HTTP | When | `retryable` |
|---|---|---|---|
| `VALIDATION_ERROR` | 400 | invalid body or parameters, including a missing `commandId` | no |
| `MODEL_OVERRIDE_FORBIDDEN` | 400 | the request tries to set `model`, `think`, `options` or `keep_alive` | no |
| `SCENARIO_NOT_FOUND` | 404 | scenario does not exist or was reset | no |
| `VEHICLE_NOT_FOUND` | 404 | unknown `vehicleId` in the scenario | no |
| `ORDER_NOT_FOUND` | 404 | unknown `orderId` in the scenario | no |
| `BARRIER_NOT_FOUND` | 404 | unknown `barrierId` | no |
| `PROPOSAL_NOT_FOUND` | 404 | proposal expired or already resolved | no |
| `BARRIER_LIMIT_REACHED` | 409 | 2 barriers are already active | no |
| `NO_FLEET_DEPLOYED` | 409 | optimize with no vehicles | no |
| `NO_ORDERS_AVAILABLE` | 409 | optimize with no orders | no |
| `SIMULATION_NOT_RUNNING` | 409 | pause a simulation that is already stopped | no |
| `SNAP_OUT_OF_RADIUS` | 422 | drop outside the snap radius | no |
| `SNAP_NO_VALID_EDGE` | 422 | drop a barrier with no candidate edge | no |
| `AI_SERVICE_UNAVAILABLE` | 503 | Ollama does not answer or is not on the internal network | yes |
| `AI_MODEL_NOT_INSTALLED` | 409 | activate or chat without `qwen3:4b` downloaded | no |
| `AI_MODEL_NOT_LOADED` | 409 | chat before `POST /api/ai/activate` | no |
| `AI_INSTALL_IN_PROGRESS` | 409 | second concurrent installation | no |
| `AI_OUTPUT_INVALID` | 502 | the model returns JSON that does not satisfy the schema | yes |
| `INTERNAL_ERROR` | 500 | unclassified failure | yes |

## 6. Scenario endpoints

All of them hang off `/api/scenarios`. `rev` marks that the operation increments
`scenarioRevision`; `—` marks that it does not touch it.

| # | Method and path | Body | Success | Errors | rev |
|---|---|---|---|---|---|
| 1 | `POST /api/scenarios` | `{}` | 201 `successResponse` | 400, 422 | new |
| 2 | `DELETE /api/scenarios/{scenarioId}` | — | 200 `scenarioRevision` | 404 | yes |
| 3 | `POST /{scenarioId}/vehicles/generate` | `{commandId, scenarioRevision, count}` | 200 `successResponse` | 400, 404 | yes |
| 4 | `POST /{scenarioId}/orders/generate` | `{commandId, scenarioRevision, count}` | 200 `successResponse` | 400, 404 | yes |
| 5 | `POST /{scenarioId}/optimize` | `{commandId, scenarioRevision, timeLimitSeconds?}` | 200 `successResponse` + `result.routePlan` | 400, 404, 409 `NO_FLEET_DEPLOYED`/`NO_ORDERS_AVAILABLE` | yes |
| 6 | `POST /{scenarioId}/simulation/start` | `{commandId, scenarioRevision, speedMultiplier?}` | 200 `successResponse` | 400, 404 | yes |
| 7 | `POST /{scenarioId}/simulation/pause` | `{commandId, scenarioRevision}` | 200 `successResponse` | 400, 404, 409 `SIMULATION_NOT_RUNNING` | yes |
| 8 | `PATCH /{scenarioId}/vehicles/{vehicleId}/position` | `{commandId, scenarioRevision, position}` | 200 `successResponse` + `result.positionSnap` | 400, 404, 422 `SNAP_OUT_OF_RADIUS` | yes |
| 9 | `POST /{scenarioId}/barriers` | `{commandId, scenarioRevision, position}` or `{..., edgeId}` | 200 `successResponse` + `result.barrierPlacement` | 400, 404, 409 `BARRIER_LIMIT_REACHED`, 422 `SNAP_NO_VALID_EDGE` | yes |
| 10 | `DELETE /{scenarioId}/barriers/{barrierId}` | — | 200 `successResponse` | 404 | yes |
| 11 | `GET /{scenarioId}` | — | 200 `scenarioRevision` | 404 | — |
| 12 | `GET /{scenarioId}/events` | — | 200 `text/event-stream` | 404 | — |

Details that cannot be deduced from the table:

- **1** The body is **empty**. The server draws the `scenarioId` and an internal
  generation seed that it never publishes, so every run is new and the client cannot
  reproduce a previous one; a legacy body with `seed` answers `422`. The scenario is
  born **empty**: no vehicles, no orders, no routes, `status: "IDLE"`,
  `scenarioRevision: 0`.
- **3** `count ∈ [1, 6]`; out of range is `400 VALIDATION_ERROR`, not a silent
  clamp.
- **4** `count ∈ [6, 24]`; orders are only placed on `DELIVERY` nodes reachable
  from the depot.
- **5** `timeLimitSeconds` accepts 1 or 2; the default is 2. The response carries
  `solverOutcome` and `objectiveIsProvenOptimal`, and the UI shows "best routes
  found", never a guarantee of optimality. An infeasible scenario returns orders in
  `unassignedOrders`, not an error.
- **6/7** They change `simulation.running` and emit telemetry over SSE. The
  simulation clock does not create new revisions.
- **8** `position` is a Three.js world point `{x, y, z}` in the local space of
  `cityRoot`. The server snaps it to the nearest node, rejects it when it exceeds the
  radius and reoptimizes **once**. `result.positionSnap` returns the requested point,
  the snapped node, the distance and whether it was accepted.
- **9** When the body carries `position`, the server snaps to the nearest edge
  excluding the already blocked ones. When it carries `edgeId`, it is validated
  against the graph. The response returns `result.barrierPlacement` and the snapshot
  already includes the edge in `blockedEdgeIds`.
- **10** Removing a barrier recomputes and compares KPIs. An unknown `barrierId` is
  `404`.
- **12** SSE stream described in section 8.

## 7. AI endpoints

Prefix `/api/ai`. The common rule: **the backend fixes the model**
(`qwen3:4b`, see `versions.md`).

| # | Method and path | Body | Success | Errors |
|---|---|---|---|---|
| 13 | `GET /api/ai/status` | — | 200 `aiStatus` | — |
| 14 | `POST /api/ai/model/install` | `{}` | 202 `installJob` (or 200 when it was already installed / in progress) | 503 |
| 15 | `GET /api/ai/model/install/events` | — | 200 `text/event-stream` | 503 |
| 16 | `POST /api/ai/activate` | `{}` | 200 `aiStatus` with `modelLoaded: true` | 409 `AI_MODEL_NOT_INSTALLED`, 503 |
| 17 | `POST /api/ai/chat` | `{commandId, scenarioRevision, messages[]}` | 200 `aiChatResponse` | 400, 404, 409 `AI_MODEL_NOT_LOADED`, 502, 503 |
| 18 | `POST /api/ai/reports/shift` | `{commandId, scenarioRevision}` | 200 `aiReportResponse` | 400, 404, 409, 502, 503 |
| 19 | `POST /api/ai/proposals/{proposalId}/confirm` | `{commandId, scenarioRevision}` | 200 `successResponse` | 404 `PROPOSAL_NOT_FOUND`, 409 |
| 20 | `POST /api/ai/proposals/{proposalId}/reject` | `{commandId, scenarioRevision}` | 200 `successResponse` | 404 |

Rules:

1. `GET /api/ai/status` distinguishes three things the UI shows separately:
   `serviceAvailable` (Ollama answers), `modelInstalled` (`qwen3:4b` is in
   `/api/tags`) and `modelLoaded` (`qwen3:4b` appears in `/api/ps` or was already
   preloaded).
2. `POST /api/ai/model/install` is **idempotent**: when the model is installed it
   answers 200 with the job in `COMPLETED`; when a download is already running it
   answers 200 with the job in progress; it only answers 202 when a new download
   starts. It never launches two simultaneous `pull` operations.
3. `POST /api/ai/activate` is a preload with `keep_alive`; it downloads nothing.
4. `/api/ai/chat` receives the conversation history and the `scenarioRevision` the
   user is viewing. The server answers using only data from the validated snapshot,
   cites the revision it used and does not expose the model's internal reasoning.
5. The chat response may include an action `proposal`. No action is applied without a
   human `confirm`; `confirm` reuses the command envelope and increments the revision
   like any other mutation.
6. Reports are validated against JSON Schema and returned in Markdown and JSON.
   If the model returns something that does not satisfy the schema: `502 AI_OUTPUT_INVALID`.
7. No request may set the model:

```json
{
  "commandId": "...",
  "scenarioRevision": 5,
  "messages": [{ "role": "user", "content": "why did the R-01 route change?" }],
  "model": "llama3"
}
```

That body answers `400 MODEL_OVERRIDE_FORBIDDEN`. The same applies to `think`, `options`
or `keep_alive`. The inference configuration (`think: false`, `num_ctx: 8192`,
temperatures, `keep_alive`) is applied by the backend proxy.

Chat response (schema `envelopes.schema.json#/$defs/aiChatResponse`, example
`examples/ai-chat-response.example.json`): `answer` (text in English), `usedRevision`
(snapshot revision it answered with), `references` (snapshot field paths that support
the answer), `proposal` (optional) and `timingsMs`.

## 8. Scenario SSE

`GET /api/scenarios/{scenarioId}/events` returns `text/event-stream` with events
named by the `event:` field.

| Event | When | Payload |
|---|---|---|
| `scenario.snapshot` | after any mutation or on connect | complete `ScenarioRevision` |
| `scenario.simulation` | every tick while `simulation.running` | per-vehicle positions + `tick` + `elapsedSeconds` |
| `scenario.optimizer` | when a computation starts and finishes | `STARTED`/`FINISHED`/`FAILED` + duration + `solverOutcome` |
| `scenario.resync` | the client asks to resume from a `Last-Event-ID` that is no longer in the buffer | reason + current revision |
| `scenario.error` | asynchronous server failure | error envelope |

Rules:

1. `id:` is `"{scenarioRevision}:{eventSeq}"`, with `eventSeq` monotonic per scenario.
   It is what the browser sends back as `Last-Event-ID` when it reconnects.
2. The server keeps a bounded buffer per scenario. When the requested `Last-Event-ID`
   is no longer there, it does not invent history: it emits `scenario.resync` and the
   client performs a `GET`.
3. Every `data:` is an object of the `events.schema.json` schema
   (`scenarioEventEnvelope` with a variant `type`).
4. The heartbeat is an SSE comment (`: ping`), not an event with a payload.
5. Simulation events do not create a revision: they are bound to the current revision
   and carry their own `tick`. That way the clock does not compete with the
   discard-by-revision rule.

Example: `examples/scenario-snapshot-event.example.json`.

## 9. Model installation SSE

`GET /api/ai/model/install/events` emits:

| Event | Payload |
|---|---|
| `ai.install` | `{ state, modelName, percent, statusText, error }` |
| `ai.status` | `{ serviceAvailable, modelInstalled, modelLoaded, modelName }` |

`state` ∈ `IDLE`, `DOWNLOADING`, `VERIFYING`, `COMPLETED`, `FAILED`. `percent` is
`null` while the backend cannot compute it and `statusText` is the status text reported
by Ollama. The contract does not fix the internal keys of the Ollama stream: the
backend translates them into these fields, so a change in Ollama does not break the
frontend. Example: `examples/ai-install-progress.example.json`.

## 10. States

```text
IDLE ──(vehicles and/or orders generated)──▶ READY
READY ──(optimize in progress)──▶ OPTIMIZING ──(done)──▶ READY
READY ──(simulation/start)──▶ RUNNING ──(simulation/pause)──▶ PAUSED ──▶ RUNNING
any state ──(DELETE /api/scenarios/{id})──▶ new scenario in IDLE
```

- `simulation.running` and `status` are coherent: `RUNNING` implies `running: true`.
- The AI state (`serviceAvailable`, `modelInstalled`, `modelLoaded`) is independent of
  the scenario state and is read through `GET /api/ai/status`.
- After `docker compose up` the scenario does not exist until the user energises the
  city; the backend never creates scenarios on its own.

## 11. Freezing and changes

- Contract version: **v1**, frozen on 2026-09-22.
- The endpoints in this table are exactly the ones that appear, with no additions, in
  `endpoints.json`; the coverage test checks that they match section 8 of the MVP
  exactly.
- Adding an endpoint or changing the semantics of `scenarioRevision` requires bumping
  `contractVersion` and updating the schemas, the examples and this document in the
  same phase.
