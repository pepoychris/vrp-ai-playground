# World and graph rules

Normative Phase 0 document. The reference implementation that satisfies it lives in
`spike/fase0/world/` and its tests in `spike/fase0/tests/`.

## 1. Coordinate system

- The world is local and flat on the ground: **XZ** plane, **Y axis up**, right-handed
  system, exactly as Three.js uses it by default.
- The unit is the **meter**. There are no degrees, latitude, longitude or map
  projection anywhere in the system.
- The origin `(0, 0, 0)` is the centre of the fictional city. Every graph node is local
  to that origin.
- `y` is the elevation of the driving surface. It is `0` across the whole city; the
  field exists so the contract does not have to be redone if a later phase adds ramps.

## 2. World ↔ graph conversion

The conversion is an explicit axis mapping, with no scaling and no swaps:

```text
graph_to_world(p) = (x = p.x, y = p.y, z = p.z)     # Three.js Vector3
world_to_graph(v) = (x = v.x, y = v.y, z = v.z)     # graph point
```

Rules derived from this:

1. **Axes are never swapped.** A graph point with `x = 3, z = 7` is world
   `(3, y, 7)`. Never `(7, y, 3)`.
2. **No axis conversion for engine convention.** If an asset with Z-up is imported one
   day, the rotation is applied to the model's scene node, not to the geometry and not
   to the graph.
3. **No scaling in the conversion.** If the visual scene is scaled to frame the
   camera, the factor lives in the transform of the Three.js `cityRoot` group and is
   never written into the graph. Every selection, projection or snap operation must run
   in the **local** space of `cityRoot` (using `Object3D.worldToLocal` before
   converting), so moving the camera or the group does not change the result.
4. **Round trip is mandatory.** `world_to_graph(graph_to_world(p)) == p` and
   `graph_to_world(world_to_graph(v)) == v` with a tolerance of `1e-9` m.

## 3. Distances and precision

- Logical distances are measured in the XZ plane: `distance_xz(a, b)` ignores `y`.
  Consequence: two nodes with the same `x/z` and a different elevation are at zero
  distance for routing. That is a deliberate decision while the city stays flat.
- The graph is serialised in JSON as `float64`. It is never rounded to compute:
  rounding is a presentation decision.
- Every comparison against zero uses the constant `EPSILON_M = 1e-9`.
- Edge lengths (`lengthMeters`) are the XZ distance between their endpoints.
  A geometry change forces them to be recomputed; the contract does not accept
  eyeballed lengths.

## 4. Stable identifiers

| Entity | Pattern | Assignment rule |
|---|---|---|
| Node | `N-001` … `N-999` | 3-digit generation index, in generation order, never reassigned |
| Edge | `E-N001-N002` | canonical pair: the lower `nodeId` lexicographically comes first |
| Vehicle | `R-01` … `R-06` | fleet index, at most 6 |
| Order | `O-001` … `O-999` | order index, at most 24 per scenario |
| Barrier | `B-1` … `B-2` | active barrier index, at most 2 |
| Scenario | UUID v4 | generated in `POST /api/scenarios` |
| Command | UUID v4 | generated by the client on every command |

Rules:

1. The `edgeId` does **not** depend on direction: `E-N002-N001` is not a valid
   identifier and never appears. Bidirectionality is expressed with
   `bidirectional: true`.
2. The generator is deterministic inside one run: the same generation order produces
   exactly the same identifiers. Every new run uses a different internal seed, so the
   client cannot force a repeated scenario.
3. Identifiers are not reused inside a scenario. On reset
   (`DELETE /api/scenarios/{id}`) a new scenario is created and the counters start
   again.

## 5. Graph rules

1. The city graph is **immutable inside a scenario**: nodes and edges do not change
   after `POST /api/scenarios`. The only thing that changes is which edges are blocked.
2. `lengthMeters` and `speedLimitKph` are per edge and symmetric with respect to
   direction.
3. Orders are placed **only** on nodes with `kind: "DELIVERY"`.
4. Every `DELIVERY` node must be reachable from the `DEPOT` node with no barriers. If a
   closure isolates an area, the order becomes `UNASSIGNED` with reason `UNREACHABLE`;
   the application does not stall and does not invent a path.
5. A graph with no valid path between two nodes does not produce zero cost: it produces
   "unreachable".

## 6. Edge blocking

1. The source of truth is `blockedEdgeIds` inside `ScenarioRevision`. It derives from
   the active barriers: `blockedEdgeIds = { b.blockedEdgeId | b ∈ barriers }`.
   `RoadEdge` has **no** `blocked` field precisely to avoid two sources of truth.
2. Placing a barrier blocks the edge **in both directions** when
   `bidirectional: true`, which is the case for every edge.
3. Routing, the distance matrix and the optimizer exclude blocked edges. There is no
   "soft" penalty on a blocked edge.
4. Removing the barrier deletes the identifier from `blockedEdgeIds` and the edge
   becomes available again with no further changes.
5. At most 2 simultaneous active barriers. A request beyond that limit answers
   `409 BARRIER_LIMIT_REACHED`.
6. A barrier cannot be placed on an edge that is already blocked: blocked edges are
   excluded from the candidates before computing the nearest one.

## 7. Node and edge snap

Radius: `SNAP_NODE_MAX_RADIUS_M = 12.0` and `SNAP_EDGE_MAX_RADIUS_M = 12.0`. They are
two separate constants even though they share a value today, so they can be split with
explicit intent.

`nearest_node(point, max_radius)`:

1. computes `distance_xz` to every node;
2. discards the ones beyond `max_radius`;
3. picks the minimum distance; on an exact tie (difference ≤ `EPSILON_M`) it picks the
   lexicographically smaller `nodeId`;
4. returns `{nodeId, position, distanceMeters}`, or `null` when there is no candidate.

`nearest_edge(point, max_radius, excluded_edge_ids)`:

1. discards the excluded edges (the already blocked ones, when placing a barrier);
2. projects the point onto every XZ segment: `t = clamp(dot(p-a, b-a) / |b-a|², 0, 1)`,
   with `t = 0` when the segment is degenerate (`|b-a| ≤ EPSILON_M`);
3. distance = `distance_xz(p, a + t·(b-a))`;
4. discards anything beyond `max_radius`;
5. picks the minimum distance and, on a tie, the lexicographically smaller `edgeId`;
6. returns `{edgeId, projectedPoint, t, distanceMeters}`, or `null`.

Contract consequences: a claw drop with no node inside the radius answers
`422 SNAP_OUT_OF_RADIUS` and the robot returns to its previous position; a barrier with
no valid edge answers `422 SNAP_NO_VALID_EDGE`. The pixel position is never blocked:
what gets blocked is an `edgeId`.

## 8. Explicit prohibitions

- Storing latitude/longitude, or using tiles, Leaflet, Mapbox, OSM or OSRM.
- Smoothing the logical route polyline: the visual route follows the edge sequence
  exactly. Smoothness belongs to the decorative road spline
  (`visualSplineControlPoints`), which is never used for computation.
- Using `Math.random()` in components: the randomness of a run lives on the server,
  which draws the internal seed when it creates it.
- Blocking "an area": what gets blocked is one graph edge.
